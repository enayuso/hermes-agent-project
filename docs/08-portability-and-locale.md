# 08 — Runtime portability and language/timezone behavior

Checked against official Claude Tag, Dots, Docker, and Python documentation on 2026-10-08. This describes the execution **host**, not the phone or laptop from which someone sends a Slack message.

## What the reference products do

- [Claude Tag](https://academy.claude.com/courses/introduction-to-claude-tag/tag-claude-and-see-what-happens) works remotely, so a thread continues after the sender closes a laptop. Its [per-thread cloud sandbox](https://claude.com/docs/claude-tag/concepts/how-it-works) is separate from the sender's OS. For routines, [Tag uses the sender's Slack profile timezone when no zone is named](https://claude.com/docs/claude-tag/users/proactivity); it stores schedules in UTC, so daylight saving changes can shift their local wall time. Claude's [language guidance](https://support.claude.com/en/articles/10769299-how-to-use-claude-in-your-preferred-language) says conversation language follows the language the person uses; interface language is a separate setting.
- [Dots](https://learn.chatgpt.com/docs/dots/computers-and-apps) lives on a cloud computer that remains available while personal devices are off. A person can separately grant access to one connected computer for local files and apps; [local work requires that computer to be online](https://learn.chatgpt.com/docs/enterprise/cloud-local-access). The public Dots docs do not describe automatic migration of a running local task to another OS or computer.

Pilot therefore must resolve **where execution runs** independently of **who sent the message**. A Windows Slack client does not make a Linux sandbox become Windows; a user in another country does not change the Docker host's OS or another member's language preference.

## Pilot's runtime rules

1. The test broker's Python launcher detects macOS/Windows hosts and uses the host loopback route. On native Linux Docker Engine it queries the default Docker bridge gateway and binds to that private interface. `PILOT_BROKER_BIND_HOST` remains an explicit override for unusual runtimes; wildcard and public binds are refused. A disposable fixed-code container probes `host.docker.internal` at startup with **no token or host mount**. A failed route stops startup. This avoids treating the Colima Unix-socket and loopback observations as a universal transport. [Docker Desktop host networking](https://docs.docker.com/desktop/features/networking/networking-how-tos/) and [Compose `host-gateway`](https://docs.docker.com/compose/how-tos/networking/) document the supported routes; other runtimes still need real deployment checks.
2. Worker commands use a bounded pipe reader/writer rather than `select()` on pipes. [Python documents that `select()` works only on sockets on Windows](https://docs.python.org/3/library/select.html). The broker still runs Linux containers on Docker Desktop/Engine; it does not attempt Windows containers or expose the host Docker API to a worker.
3. The owner agent timezone comes from a valid `AGENT_TIMEZONE` override, otherwise the owner's Slack profile, otherwise the execution host's IANA timezone, otherwise UTC. `poc/scripts/init.py` and `detect-timezone.py` provide Python setup entry points on all three host systems; `.sh` files are POSIX wrappers. Native Windows setup needs `tzdata` for IANA validation and `tzlocal` for the host-zone fallback ([Python `zoneinfo`](https://docs.python.org/3/library/zoneinfo.html), [tzlocal](https://github.com/regebro/tzlocal)). `poc/requirements-host.txt` lists them. The sender's Slack timezone and language setting are attached **per message**; the language setting is now retained even if the sender profile has no timezone.
4. Reply language follows the message itself. For wordless turns, it follows the conversation, then the sender's Slack language setting. Scheduled work uses an explicit place preference or recent human language. Device OS, IP location, and timezone are never language signals. This is a Pilot behavior rule, not a claim about a published Claude Tag language algorithm.

## Limits before a portable release

- The broker and route probe have been exercised on **macOS with Colima** only. The Windows and Linux branches have unit tests but still need native live tests, including Docker Desktop Windows and native/rootless Linux. On rootless Linux, [Docker notes that CPU/memory/process limits require cgroup v2 and systemd](https://docs.docker.com/engine/security/rootless/tips/); verify enforcement rather than relying on flags alone.
- The broker is a **same-host** service. Plain HTTP plus a local bearer token must not be stretched across a WAN or remote Docker daemon. A distributed/cloud deployment needs a mutually authenticated, encrypted control channel and placement-aware workers. The client device's geography should not select a different data location by accident.
- Native Windows token provisioning currently requires an ACL-protected token file supplied by the installer or operator. Core bootstrap now has a Python entry point; routine setup, smoke, and behavior scripts still need portable entry points or a documented WSL2 path. Windows setup must use Docker's **Linux containers** backend.
- Command cards and some operator-created routine prompts are English today. Multilingual model behavior, command UI copy, scheduled posts, Unicode file paths, and daylight saving transitions need tests across representative languages/zones. This work should not be inferred from Korean and English smoke checks alone.

## Checks completed on 2026-10-08

- Eight broker unit checks, three timezone checks, and two portable bootstrap checks passed. The live macOS/Colima broker route probe passed, as did separate-worker scratch, timeout, excessive-output, and release/rebuild tests. Stopping a broker with an active worker removed it; no labeled workers remained. The broker was then stopped. The full Python bootstrap also completed against the existing local PoC without changing its selected timezone.
- The Slack reader regression passed inside a disposable, no-network Hermes container: a `fr-FR` language setting survived a profile with no timezone. The updated plugin and language instructions were synchronized to the live gateway, which restarted once and returned HTTP 200. `init.sh` now also syncs the shared `SOUL.md` into personal DM profiles; the owner's copy matches the service copy, and pinned Hermes loads the profile file when composing the prompt. The sandbox plugin is present but **not enabled**; `terminal.backend` remains `local`.
- No Windows or Linux host test has been run yet. The source and unit checks establish intended branches; they are not evidence that those platforms already work end to end.
