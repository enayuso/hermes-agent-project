## Product behavior: distinguish the two execution models

| Question | Claude Tag (preferred for Slack behavior) | Dots |
| --- | --- | --- |
| Where work runs | An ephemeral cloud sandbox for each Slack thread; a channel-level session is separate. Two threads do not share sandbox state. | The dot has its own cloud computer and browser, which can keep state between periods of use. It can create separate cloud or local Work/Codex tasks. The public docs do not promise a sandbox per Slack thread. |
| Quiet/idle thread | A Slack thread Claude has never joined has no Claude working session yet. A few minutes after a **finished turn**, an existing session's sandbox is released. The Slack thread, session transcript, channel memory, and externally posted/pushed work remain. A reply resumes the same thread session in a fresh sandbox; files left only in the old sandbox are lost. A thread's session has no published idle-age reset. | The dot can pause and wake to continue assigned work; its computer can keep state. Pausing the main task, stopping a delegated task, and canceling a schedule are distinct. The docs do not specify an idle Slack-thread sandbox timeout. |
| Session replacement/failure | `!restart` archives the old session and rereads the thread in a new one; a stuck/failed session is replaced on the next message. Deleting a thread's first message closes and archives its session. Channel-level sessions are replaced after about an hour of channel inactivity, a changed configuration, or about a day of age after work goes quiet. These defaults are approximate and **do not** reset thread sessions. A queued session waits for capacity; failed-start and interrupted turns have explicit retry notices. | The dot and its delegated tasks are independently controlled and reviewed in Activity/Scheduled. Public Dots docs do not specify Claude Tag-style Slack thread session replacement. |
| Credentials and outbound network | The sandbox has no provisioned credentials. Agent Proxy injects them at the boundary for an allowed host/path/method; other requests are denied. The hosted network defaults to restricted/trusted destinations, and private/metadata endpoints remain blocked. Channel work uses scoped service accounts; one-to-one DMs use the member's account/connectors. | Messaging access, app/plugin access, and local-computer access are separate grants. The dot's cloud browser has separate sessions from the user's browser. OpenAI documents action review and app permissions, but does not claim Claude Tag's per-thread Agent Proxy architecture for Dots. |
| Usage | Channel/group-DM working sessions draw on an organization balance with organization and default/per-channel caps; linked personal DMs follow the sender's seat limits. Work that would exceed a cap is declined with an explanation; the setup guide also describes an in-progress turn stopping if a limit is reached. Throughput/rate limits are separate and may queue or briefly delay work. | Conversation with a dot does not count toward ChatGPT usage limits. Deeper work has a plan allowance; Work/Codex tasks it starts use those products' normal limits. Public documentation provides no fixed Dots allowance here and no Claude Tag-like per-Slack-channel spend cap. |

Sources: [Tag lifecycle and idle behavior](https://claude.com/docs/claude-tag/concepts/how-it-works), [Tag security boundary](https://claude.com/docs/claude-tag/concepts/security-and-data), [Tag data lifecycle](https://claude.com/docs/claude-tag/concepts/data-lifecycle), [Tag failures and queue](https://claude.com/docs/claude-tag/users/troubleshooting), [Tag spend policy](https://claude.com/docs/claude-tag/admins/set-spend-limit), [Tag channel limits](https://claude.com/docs/claude-tag/admins/restrict-access), [OpenAI Docs: Dots computer and apps](https://learn.chatgpt.com/docs/dots/computers-and-apps), [OpenAI Docs: Dots overview/limits](https://learn.chatgpt.com/docs/dots).

Do not apply Anthropic *Managed Agents* sandbox-retention numbers or Codex cloud-task lifetimes to Claude Tag: they are different product documentation. In particular, Tag's published behavior is release after a few minutes of quiet, with durable transcript but ephemeral worker files. Its beta transcripts and memory currently have **no automatic retention period**; deletion is a separate operation, not idle cleanup.

## Measured Pilot/Hermes behavior

- Before the pilot, Pilot had one credential-bearing Hermes container, with a service profile for channels/group DMs and one personal profile for the owner's one-to-one DM. `terminal.backend: local` let terminal **and file tools** run inside that same container and shared bind-mounted data directory. Profile routing isolated selected Hermes state; it was not a process, filesystem, or network boundary.
- The pinned Hermes Docker backend with `container_persistent: false` keys a sandbox by the gateway's durable session ID, and its file tools use the same environment. Such a sandbox survives between turns, then the idle reaper removes it after the configured inactivity period (default `TERMINAL_LIFETIME_SECONDS=300`, checked once per minute). Active tracked background processes refresh activity. A new call recreates the sandbox. Session-scoped Docker containers disable cross-process reuse. For this gateway, Hermes passes `session_entry.session_id` as the turn `task_id`; this gives a plausible per-thread mapping but still needs a live two-thread test. Cron/background task identity needs its own test.
- The Docker backend can enforce CPU/memory limits, `docker_network: false`, and optional egress proxy enforcement. Its nonpersistent workspace is temporary. **However**, `docker_volumes`, automatic cwd mounts, skill/credential-file read-only mounts, explicit `docker_forward_env`, and implicit skill/environment passthrough can reintroduce secrets or shared paths. The latter must be measured and blocked for untrusted workers. A credential file mounted read-only is still readable by the model's code.
- Docker isolation here covers shell/file operations only. Browser, plugin, MCP, gateway, Slack, memory, model calls, and approval code remain in the gateway process unless each is explicitly moved or separately constrained. The new boundary must be verified tool by tool rather than inferred from `terminal.backend`.
- The gateway has a Docker CLI but no daemon socket. Setting `terminal.backend: docker` directly would make its shell/file tools fail. Mounting an unrestricted Docker socket into this credential-bearing gateway gives it host-level Docker control and defeats the boundary. A disposable host-launched container using the pinned Hermes image passed a local baseline check with no mounts, `--network none`, `--read-only`, non-root UID, all capabilities dropped, `no-new-privileges`, process/CPU/memory limits, and a small writable `/tmp`; this validated host capability before gateway integration.
- Hermes' SSH backend accepts a static host/user/port/key per profile and syncs local Hermes files to that host. It cannot, by changing `terminal.backend` alone, allocate a new worker per Slack thread.

The last four bullets are source/host observations, not claimed Claude Tag parity. [Docker daemon security](https://docs.docker.com/engine/security/) is the basis for withholding the socket from the gateway.

## Restricted worker development and live pilot, 2026-10-08

`poc/sandbox/broker.py` and `poc/plugins/pilot-sandbox/` implement the Hermes terminal/file backend used by the pilot. The broker is bound to `127.0.0.1:8787`, with a private bearer token and fixed create/exec/release operations. It uses the host user's Docker CLI. Neither the gateway nor any worker receives the Docker daemon socket. The gateway-facing adapter uses Hermes' custom terminal provider interface and the same environment for shell and file operations. Session IDs are validated and hashed for Docker names; all 24 API, cron, and Slack session IDs checked before the switch matched the broker's accepted syntax. The live gateway now uses `terminal.backend: pilot_sandbox`.

Each lazily created worker uses a fixed pinned image, `--network none`, a read-only root, UID/GID 65532, dropped capabilities, `no-new-privileges`, CPU/memory/process limits, no host mounts, and only bounded tmpfs scratch. The `/workspace` tmpfs must set `uid=65532,gid=65532,mode=0700`: the first live smoke exposed that Docker's default root-owned tmpfs blocked the unprivileged worker's writes. This option is documented by [Docker tmpfs mounts](https://docs.docker.com/engine/storage/tmpfs/). The broker caps command size, output, runtime, and worker count; a timeout or excessive output destroys that worker. Ordinary shell exit codes 124 and 125 do not destroy it. A 300-second idle reaper drops quiet workers; Hermes keeps the durable session separately. A broker restart also clears its old labeled workers.

The host integration test passed: a command ran as UID 65532 with no gateway data or Docker socket, session A's scratch file was invisible to session B, a normal `exit 124` kept A's scratch, timed-out and excessive-output commands destroyed A's worker, and release/rebuild started with empty scratch. The Hermes adapter also executed through the broker from a separate disposable client container using only a read-only token mount. The broker now detects its local host route and verifies it with a token-free Docker probe at startup; the command pipe implementation is portable to Windows. Only the macOS/Colima path has been run live. See [08](08-portability-and-locale.md) for the platform matrix and limits. This verifies the narrow terminal path, not the whole agent boundary.

**Remaining after the pilot switch:** validate real Slack-thread and cron task identities through Hermes, exercise a two-thread Slack run and gateway restart, and verify visible Slack failure/queue messages. The current broker permits bounded credential-free public search and exact-host HTTPS fetch; credential-mediated connector access remains future work. In particular, pinned Hermes' `browser_exec` runs arbitrary Python in the gateway process when the browser-use backend is selected, even when the terminal tool is available; merely changing the terminal provider would leave a host-execution route. `web_search`/`web_extract` and enabled MCP/plugin tools also execute gateway-side. A worker with `--network none` reaches approved public destinations only through the broker tools; general repository/package network access is unavailable. The host broker's bearer token is a local control-plane secret; it must remain outside all model-readable paths. The pilot is now live; see the switch record below.

Before the switch, `hermes tools list --platform slack` marked `web`, `browser`, `terminal`, `file`, `code_execution`, `skills`, `connections`, `delegation`, `cronjob`, and `computer_use` toolsets enabled (individual availability checks may remove specific tools). Pinned `execute_code` **does** switch its Python process to the selected remote terminal backend when `env_type != local`, but its RPC bridge can call a subset of gateway tools; that bridge is disabled in the pilot pending its own allowlist audit. The browser-use `browser_exec` code path is different: it runs Python in the gateway, so it is disabled by the pilot tool policy. `computer_use` has a separate availability gate; its CLI toolset marker alone does not prove it is callable. ### Candidate tool policy and first egress route

`poc/config/boundary-tool-policy.yaml` is a staged policy for Slack, cron, and the API server. `poc/scripts/check-boundary-tools.py` resolves **actual tool names** through pinned Hermes before accepting it, including the scoped memory provider's two schemas that Hermes appends after its normal registry snapshot. The policy keeps terminal/file tools, scoped Slack reads, memory, routine controls, bounded `web_fetch`, and fixed-destination `public_web_search`; it removes gateway browser Python, browser vault, built-in web, `execute_code`, skills, project switching, delegation, connections, and desktop control from these agent surfaces. The API server receives no model tools during the first cutover. Cron jobs with a per-job toolset override outside the cron allowlist cause the check to fail. Hermes also auto-enabled plugin toolsets on the API even with `platform_toolsets.api_server: []`; `known_plugin_toolsets` is required to make that empty list effective, and the checker rejects an unreviewed plugin addition. It passed candidate resolution before the switch and now passes active startup checks for both the service and personal profiles in the pinned container: 17 Slack tools, 16 cron tools, and zero API tools. The new search tool uses a distinct name because registering another `web_search` collided with Hermes' built-in tool.

`poc/sandbox/egress.py` and the broker's `/fetch` operation add a credential-free HTTPS-only route for text/JSON. An absent policy defaults to **no allowed hosts**. For the first pilot the user approved existing search and public GitHub; `poc/config/egress-policy.json` now names exactly `search.parallel.ai`, `github.com`, `api.github.com`, and `raw.githubusercontent.com`. The broker needs `PILOT_EGRESS_POLICY_FILE` set to this file to use those hosts. It checks every resolved address for public routability, connects to a checked address while validating TLS for the named host, sends only fixed headers, refuses redirects and compression, and bounds the URL, time, and response size. The `pilot-sandbox` plugin exposes this as `web_fetch` only when that plugin and toolset are enabled. A denied host returns a specific refusal. A worker remains `--network none` and receives no key. Unit tests cover exact-host matching, private/metadata DNS, redirect refusal, multilingual URL paths, broker authorization, and default denial.

The broker's `/search` operation uses the fixed `search.parallel.ai/mcp` keyless endpoint and Hermes v2026.9.24's observed `web_search` MCP payload. ## Usage evidence and limit shape

- `poc/scripts/report-usage.py` reads lifetime `session_model_usage` totals by service channel, personal DM, API, and scheduled work, but those rows are cumulative per session. `pilot-usage` records physical `post_api_request` **and** `post_auxiliary_call` events without prompts or replies; `poc/scripts/report-request-usage.py` gives a time-windowed ledger by verified place. Two live API calls, including auxiliary title generation, reconciled exactly with Hermes' model-usage rows. Synthetic source checks covered service channel, personal DM, and scoped cron origins. Real Slack/cron calls still need reconciliation. The audit starts at deployment, so it is not a historical billing ledger.
- On 2026-10-08 the last-24-hour request ledger contained only three API physical calls (one auxiliary), 32,068 input tokens and 48 output tokens. That is not enough channel/DM/cron data to set production caps. The self-hosted model reports **unknown cost** and `$0`; `$0` must not be used as a spend measurement. GPU occupancy/time and concurrency are not yet measured. Capacity and whether scheduled jobs share a channel budget also need explicit policy.
- The pinned Hermes `pre_llm_call` hook only injects context; `pre_api_request` is an observer whose errors are swallowed. Request middleware also catches failures and continues. Thus a usage cap implemented solely in these plugin hooks would fail open. Admission must be enforced at a verified gateway ingress or provider boundary that can decline a turn and its auxiliary calls before any model work, with an atomic reservation and an explicit user-facing response.

## Implementation sequence and acceptance criteria

1. Keep the Slack ingress and its stored transcripts, notes, routines, and approved connector authority in a control plane. Give each personal DM its own agent identity. Add a **narrow** host-side sandbox broker: the gateway may request create/exec/stop only for a verified session identity and a fixed image/policy, never arbitrary Docker options, host paths, or credentials. The broker alone holds Docker authority. Integrate Hermes' terminal/file environment with that broker, or use a worker protocol that moves the whole agent turn; do not enable the native Docker backend with an unrestricted socket.
2. On first work in a thread, create a restricted disposable worker. Reuse it during a turn and for a short quiet window, then stop/remove it while keeping the durable Hermes session. The next reply recreates a clean worker for the **same** session. Publish or push artifacts that must survive; do not promise scratch-file persistence. Handle stop, restart, failed worker, gateway restart, cron, and background processes explicitly. Ensure a queued request cannot be mistaken for a finished or lost one.
3. Prove two simultaneous threads, two channels, and a personal DM cannot read each other's files, environment, session data, credentials, or host Docker API. Assert worker mount/env allowlists, non-root and resource limits, network deny by default, permitted HTTP(S) destinations through a credential broker, and blocked private/metadata destinations. Check every exposed tool, including browser and connectors, for a bypass. A failed broker or policy layer must fail closed with a useful Slack error.
4. Reconcile real Slack and cron usage at the next scheduled fire. Record GPU-time/concurrency and a representative mix of turns. Then choose explicit allowances and reset periods, implement atomic admission plus bounded turns and distinct throughput handling, and verify rejected/queued work causes no model call. Test threshold alerts, reset, routine origin charging, personal DM routing, and accepted work completing under its reserved budget.

Outlook remains disabled at the user's direction. Personal-connector consent and channel result review can be exercised only with a connector and an explicit access boundary.
