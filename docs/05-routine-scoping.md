## Behavior checked before implementation

- [Claude Tag routines](https://claude.com/docs/claude-tag/users/proactivity): a routine belongs to the channel where it was set up, uses that channel's connections, and channel members can manage it. A channel watch may read named channels and report back to its origin. Results may go to another *public* channel under documented conditions; this PoC currently restricts routine delivery to its origin until membership and destination checks exist.
- [Claude Tag `!routines`](https://claude.com/docs/claude-tag/users/commands): lists only the channel's routines. A cross-channel request requires membership and gives an ephemeral response. The PoC's `routines_list` tool handles the current place only; the exact Slack command and cross-channel form are still open.
- [Claude Tag memory](https://claude.com/docs/claude-tag/users/memory): a channel reads its own notes and workspace notes; DMs read their own notes. [Dots recurring work](https://learn.chatgpt.com/docs/dots/tasks-and-memory) has a saved schedule with its own instructions and destination. Where they differ, the PoC follows Claude Tag's place model.
- Hermes `v2026.9.24` source in the container: `tools/cronjob_job_args.py::_origin_from_env` stores a chat-created job's origin; `cron/jobs.py` persists it; `cron/scheduler.py::_CronRunScope` deliberately clears chat session variables for cron; `tools/cronjob_tools.py::_action_list` returns every job in the profile. `cronjob` also supports `context_from` references to other jobs' output. These facts determined the implementation.

## What changed

- `pilot-memory` resolves `cron_<job id>_<fire time>` to the stored job origin and loads that channel's or DM's notes read-only. An unscoped job sees no place or workspace notes. Cron's sender/session variables remain cleared.
- `pilot-routines` adds `routines_list` filtered by origin chat and, when present, workspace. Its `pre_tool_call` hook blocks profile-wide `cronjob_manage`/`cronjob` listing, cross-place management, cross-place `context_from` dependencies, and delivery outside the origin. Unknown origins fail closed. Interactive creation in Slack retains Hermes' automatic origin capture.
- The two public, operator-created jobs (`channel-watch`, `weekly-agent-landscape`) had `origin: null` and delivered to `SLACK_HOME_CHANNEL`. `provision-routine-origins.py` first verifies each resolved target is that channel, then records it as origin and switches delivery to `origin`. The paused personal `morning-briefing` remains unscoped and hidden until it can be placed in the owner's isolated DM profile.
- The first `channel-watch` run completed and delivered at 18:01 KST. Its digest incorrectly treated the agent's own unanswered suggestions as human follow-ups and claimed notes were empty while a channel note existed. The prompt now excludes the former and tells the agent to check notes before making memory claims.

## Verification and remaining limits

- Scope tests: memory 27 checks, routines 15 checks. Hermes registry dispatch: two routines visible in the test channel, zero in the owner's DM; global list and cross-delivery calls blocked. Direct provider initialization for both scoped jobs loaded the test channel's one note read-only; the paused briefing loaded none. Gateway restarted and Slack reconnected.
- The exact `!routines` Slack command lists the current conversation's scheduled jobs in a thread without starting a model turn. It accepts a bare command in an explicitly configured free-response channel or a DM, and an addressed command elsewhere. A single channel mention or ID lists another internal channel's jobs only after Slack verifies that both the requester and the bot belong to it; the response is ephemeral. The command uses the routed profile's cron store, so a personal DM cannot list service-profile jobs. Hermes only stores scheduled jobs here; Claude Tag's other standing-work types are not represented yet.
- On 2026-10-08, the first live `!routines` in `#pilot-agent-test` reached Hermes as an ordinary model turn: the Slack event contained no bot mention. The parser now follows Hermes' configured free-response channel policy, and a regression test covers that exact event. The second live command bypassed the model and listed both scoped jobs, but Slack retried the event and posted duplicate replies. Slack Bolt's actual dispatcher returns 404 when global middleware stops without a response; the middleware now returns `BoltResponse(status=200)` for consumed commands and muted messages. An in-container middleware check verified one post, a 200 response, and no model-listener call. The third live command at 10:19 KST posted exactly one thread reply with both jobs; its count remained one after the retry window, and the gateway recorded no model turn.
- The user's screenshots at 10:25 KST showed the list exposing raw cron expressions (`0 9 * * 1`) and UTC timestamps without a local reading. [Claude Tag documents](https://claude.com/docs/claude-tag/users/commands) the list's channel scope, thread/private placement, and [UTC schedule confirmation](https://claude.com/docs/claude-tag/users/proactivity), but does not publish an exact list template. The Pilot Agent reply now describes simple Hermes cron schedules as weekdays and local times, adds the next local and UTC run, labels paused jobs, and calls the place "this channel" or "this DM." Unsupported cron forms retain their stored expression rather than being guessed. The existing two jobs produce "Every Monday at 09:00 Asia/Seoul" and "Every weekday at 18:00 Asia/Seoul." Live rendering after this copy change remains to be checked.
- This hook scopes the **cronjob tool**, not the shared terminal, files, scripts, skills, or credentials. Those are still common to the single Hermes profile; per-person profiles and per-thread sandboxing are required before claiming full isolation. The hook also checks access before Hermes dispatch rather than in Hermes' job-store transaction.
- A live next scheduled fire with the new origin-aware memory has not yet occurred. The provider path was exercised directly; inspect the next job's log for the resolved channel and review its output.
